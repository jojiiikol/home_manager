# Домашний менеджер

Веб-приложение для совместного ведения домашних дел, заметок и учёта коммунальных услуг.

## Основная идея

Дом — общее пространство пользователей. Участники дома видят его дела и заметки и могут добавлять свои записи. Данные разных домов должны быть изолированы друг от друга.

## Планируемые возможности

### Совместные дела и заметки

- Добавление домашних дел и заметок.
- Просмотр записей всех участников своего дома.
- Учёт выполнения дел.

### Коммунальные услуги

- Ежемесячное внесение показаний счётчиков воды, электроэнергии и отопления.
- Хранение истории показаний.
- Отображение потребления на графиках.
- Учёт сумм коммунальных расходов.

Способ учёта сумм — ручной ввод, расчёт по тарифам или их сочетание — предстоит определить.

## Стек

- Python и FastAPI — серверная часть и API.
- PostgreSQL — база данных.
- Docker и Docker Compose — запуск приложения и его инфраструктуры.

Технологии интерфейса пока не выбраны. Разделы функциональности не предполагают обязательного разделения на отдельные микросервисы.

## Текущее состояние

Подготовлен инфраструктурный каркас на Python 3.14: FastAPI, конфигурация окружения, подключение к PostgreSQL, Alembic, Docker Compose и Nginx. Реализован сервис пользователей: регистрация, вход, просмотр профиля, изменение имени и смена пароля. Дела, дома и учёт коммунальных услуг пока не реализованы. Приложение запускается через `src.main:app`.

## Структура

```text
src/
  main.py             # Сборка FastAPI, подключение роутеров и lifespan
  config.py           # Настройки и URL подключения к PostgreSQL
  database.py         # Async engine, сессии и базовый класс моделей
  routes/             # HTTP-эндпоинты, статусы и обработка запросов
  services/           # Бизнес-логика и сценарии использования
  repositories/       # Запросы к БД и другим хранилищам
  dto/                # Внутренние структуры передачи данных между слоями
  schemas/            # Pydantic-схемы запросов и ответов API
  models/             # ORM-модели таблиц
  security/           # Хэширование паролей и проверка JWT
  exceptions/         # Ошибки сценариев и доступа к данным
alembic/              # Окружение и версии миграций
nginx/default.conf    # Reverse proxy к API
tests/                # Проверки конфигурации и API
Dockerfile
compose.yaml
requirements.txt      # Зафиксированные зависимости приложения
requirements-dev.txt  # Зависимости приложения, тестов и линтера
```

Разработка следует принципам чистого кода. Роуты вызывают сервисы, сервисы обращаются к репозиториям. Внутренние DTO не зависят от HTTP и ORM, а схемы описывают внешний контракт API. Модули внутри слоёв называются по предметной области. Например, проверка готовности проходит через `routes/health.py` → `services/health.py` → `repositories/health.py`; SQL остаётся в репозитории. Простая проверка процесса `/health` не обращается к хранилищу.

## Запуск через Docker Compose

Нужны Docker Engine (или запущенный Docker Desktop) и Docker Compose v2.

```bash
cp .env.example .env
# Установите свой POSTGRES_PASSWORD и случайный JWT_SECRET_KEY в .env.
docker compose up --build -d
docker compose ps -a
docker compose logs -f api
```

Если `.env` уже существует, используйте его без перезаписи. Локальный `.env` исключён из Git и Docker build context.

Порядок запуска: PostgreSQL становится доступен, одноразовый сервис `migrate` выполняет `alembic upgrade head`, затем запускается API, а после успешной проверки его готовности — Nginx. Успешное завершение `migrate` с кодом 0 ожидаемо. API работает от непривилегированного пользователя и не публикует отдельный порт на хосте.

- [Swagger UI](http://localhost:8080/docs).
- [OpenAPI](http://localhost:8080/openapi.json).
- [Проверка процесса API](http://localhost:8080/health).
- [Проверка доступности БД](http://localhost:8080/health/ready): возвращает 503 при ошибке подключения.

Nginx принимает HTTP на `127.0.0.1:8080`, PostgreSQL — подключения на `127.0.0.1:5432`. Порты меняются в `.env`. Это конфигурация локального запуска; HTTPS и внешний домен пока не настроены. Доверие API к proxy-заголовкам рассчитано на доступ через Nginx внутри сети Compose.

```bash
docker compose down
```

Остановка сохраняет данные в именованном томе `postgres_data`. Команда `docker compose down -v` удаляет этот том вместе с данными. Настройки пользователя, пароля и имени БД в образе PostgreSQL применяются при первой инициализации пустого тома; изменение `.env` не меняет существующую БД.

## Конфигурация

Настройки читаются через Pydantic Settings из `.env` в корне проекта и переменных окружения. Переменные окружения имеют приоритет. URL PostgreSQL собирается через SQLAlchemy `URL.create`, включая корректное экранирование специальных символов пароля; готовую строку подключения в `.env` хранить не нужно.

| Переменная | Назначение |
| --- | --- |
| `APP_NAME` | Название приложения в OpenAPI |
| `DEBUG` | Режим отладки FastAPI, по умолчанию выключен |
| `JWT_SECRET_KEY` | Обязательный секрет подписи JWT, минимум 32 символа; генерируйте случайное значение |
| `POSTGRES_HOST` | Адрес БД для локального API; в Compose заменяется на `db` |
| `POSTGRES_PORT` | Порт БД для локального API; в Compose заменяется на `5432` |
| `POSTGRES_DB` | Имя БД, обязательно |
| `POSTGRES_USER` | Пользователь БД, обязательно |
| `POSTGRES_PASSWORD` | Пароль БД, обязательно |
| `POSTGRES_PUBLISHED_PORT` | Порт PostgreSQL на хосте, по умолчанию `5432` |
| `HTTP_PORT` | Порт Nginx на хосте, по умолчанию `8080` |

## Локальная разработка

```bash
python3.14 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
docker compose up -d db
alembic upgrade head
uvicorn src.main:app --reload
```

Локальный API доступен по адресу [localhost:8000/docs](http://localhost:8000/docs). Если изменён `POSTGRES_PUBLISHED_PORT`, для локального API задайте такой же `POSTGRES_PORT`.

## Миграции

Начальная ревизия `0001` задаёт отправную точку; `0002` создаёт таблицы пользователей и профилей. Таблица `alembic_version` создаётся Alembic при применении миграций. Не используйте `Base.metadata.create_all()` вместо миграций приложения; в изолированных тестах допускается создание схемы из metadata.

После добавления моделей на основе `src.database.Base` импортируйте их модули в `alembic/env.py`, чтобы Alembic видел metadata. Для локальной разработки:

```bash
alembic revision --autogenerate -m "describe schema change"
# Проверьте сгенерированные upgrade() и downgrade().
alembic upgrade head
alembic current
alembic downgrade -1
```

Для уже собранного окружения:

```bash
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic upgrade head
```

Создавайте новые ревизии локально: исходники не примонтированы в контейнер, и созданный внутри него файл не сохранится в репозитории. После изменения кода или миграций выполните `docker compose up --build -d`.

## Зависимости и проверки

Для установки достаточно `pip install -r requirements.txt`. Файлы `.in` содержат прямые зависимости, `.txt` фиксируют также транзитивные версии. Для обновления нужен `uv`:

```bash
uv pip compile requirements.in -o requirements.txt --python-version 3.14 --no-emit-index-url
uv pip compile requirements-dev.in -o requirements-dev.txt --python-version 3.14 --no-emit-index-url
```

SQLAlchemy используется для работы с БД, Psycopg — как асинхронный драйвер PostgreSQL, Alembic — для миграций. HTTPX и pytest нужны для проверок API, Ruff — для проверки стиля.

```bash
pytest
ruff check .
ruff format --check .
docker compose config --quiet
```

Тесты конфигурации и HTTP-проверок не требуют запущенной PostgreSQL. Сценарии пользователей проверяются через API на временной SQLite с включёнными внешними ключами (`aiosqlite` — только зависимость для разработки). PostgreSQL остаётся основной БД; SQLite не проверяет особенности блокировок и конкурентных транзакций PostgreSQL. Проверка реальной цепочки Nginx → API → PostgreSQL выполняется после запуска Compose через `/health/ready`.

## Пользователи и авторизация

Учётные данные хранятся в `users_table`: `id` (UUID), уникальный `username`, `password_hash`, `created_at`, `updated_at`. Профиль хранится в `users_info_table`: `user_id` (одновременно PK и FK на `users_table.id`), nullable `name`, `created_at`, `updated_at`. Связь один к одному, удаление пользователя каскадно удаляет профиль. Регистрация создаёт обе записи одной транзакцией, с `name = null`.

Имена таблиц: сущность во множественном числе с суффиксом `_table`; для расширения родительской сущности — `<родительская сущность>_<дополнительная сущность>_table`.

| Метод и путь | Доступ | Действие |
| --- | --- | --- |
| `POST /users` | Без токена | Регистрация: `username`, `password`; ответ 201 с `id`, `username`, `additional_info`, `created_at`, `updated_at` |
| `POST /auth/token` | Без токена | Вход по JSON с `username` и `password`; ответ с access-токеном |
| `GET /users/me` | Bearer JWT | Свой профиль: `id`, `username`, `additional_info`, `created_at`, `updated_at` |
| `PATCH /users/me` | Bearer JWT | Обновление имени: `{"name": "Анна"}`; `null` очищает имя |
| `PUT /users/me/password` | Bearer JWT | Смена пароля: `old_password`, `new_password`; успех — 204 |
| `GET /users/{user_id}` | Bearer JWT | Просмотр другого пользователя: `username`, `additional_info`, `created_at`, `updated_at` |

Для защищённых запросов передавайте `Authorization: Bearer <access_token>`. В Swagger UI сначала вызовите `/auth/token`, затем вставьте полученный `access_token` в **Authorize**.

Пароли хэшируются Argon2 через `pwdlib`. Хэш пароля не возвращается API. Проверка пароля выполняется в рабочем потоке, чтобы не блокировать event loop. JWT подписываются и проверяются через `PyJWT` с фиксированным алгоритмом HS256, обязательными `sub`, `iat`, `exp` и сроком действия **15 минут** (`expires_in = 900`). Секрет задаётся через `JWT_SECRET_KEY`; пример генерации:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Refresh-токены и отзыв выданных токенов пока не реализованы. После смены пароля новые входы требуют нового пароля, а ранее выданные JWT действуют до истечения срока. Пользователь из токена дополнительно проверяется в БД.

Логин чувствителен к регистру, состоит из 3–64 латинских букв, цифр, `.`, `_`, `-` и пока не меняется через API. Новый пароль — от 8 до 128 символов. Имя — от 1 до 100 символов после удаления пробелов по краям либо `null`. Лишние поля запросов отклоняются. Время хранится в UTC; `updated_at` изменяется при записи в соответствующую таблицу через SQLAlchemy.

Дубликат логина возвращает 409, неверные учётные данные или токен — 401, неправильный старый пароль — 400, отсутствующий пользователь — 404, ошибки входных данных — 422. Изменять чужой профиль или пароль через API нельзя.

Правила работы с репозиторием для агентов описаны в [AGENTS.md](AGENTS.md).

В ответах профиля `created_at` — дата создания учётной записи, а `updated_at` — наиболее поздняя дата изменения из `users_table` и `users_info_table`, включая смену пароля и обновление имени. Эти даты доступны при просмотре себя и других пользователей по токену.

Ответы пользователей содержат вложенный профиль `"additional_info": {"name": "Саша"}` (после регистрации — `{"name": null}`). Репозиторий загружает ORM-связь `User.info` через `selectinload`, преобразует её во вложенный DTO, а Pydantic-схемы с `from_attributes=True` формируют JSON. ORM-объекты остаются внутри репозитория. Формат запроса обновления имени прежний: `{"name": "Саша"}`.
