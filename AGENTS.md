# Инструкции для агентов

Эти инструкции действуют для всего репозитория.

## Контекст проекта

Домашний менеджер — веб-приложение для участников одного дома. Первые функциональные области: совместные дела и заметки, а также учёт коммунальных услуг. Описание продукта и текущее состояние находятся в [README.md](README.md).

Согласованный стек: Python, FastAPI, PostgreSQL, Docker и Docker Compose. В `.python-version` указана версия Python 3.14. Интерфейс: React, TypeScript и Vite; исходники находятся в `frontend/`. Nginx обслуживает SPA и проксирует `/api/` к FastAPI.

## Работа над задачами

- Перед изменениями изучай существующий код и инструкции в затрагиваемых каталогах.
- Выполняй текущую задачу без добавления несогласованной функциональности и масштабных побочных переработок.
- Сохраняй изменения пользователя. Не откатывай и не перезаписывай посторонние правки.
- Различай реализованные возможности, планы и предположения. Не описывай запланированное как работающее.
- Не добавляй зависимости и отдельные сервисы без необходимости для задачи. Выбор дополнительных библиотек объясняй.
- Обновляй README при изменении способа установки, запуска, конфигурации или фактических возможностей приложения.

## Предметная область и доступ

- Дом хранится в `houses_table`, название — в `houses_info_table` (PK/FK `house_id`, связь один к одному); хэш пароля — `password_hash`. Логин дома уникален и изменяем, название обязательно.
- Участие хранится в `houses_participants_table`: `id`, `house_id`, `user_id`, `role`, `status` и даты; пара `(house_id, user_id)` уникальна. Роли: `admin`, `member`; статусы: `active`, `blocked`, `left`. Создание дома атомарно создаёт информацию и активного админа-создателя.
- Все операции домов требуют JWT. Любой существующий участник, включая `left` и `blocked`, видит основные данные дома и свою связь. Список всех участников доступен только активным участникам, изменение дома и управление участниками — только активным админам.
- Вступление требует логин и пароль дома. Активному участнику возвращай 409; заблокированному отказывай во вступлении. Вышедший вступает с обновлением прежней связи и ролью `member`; строки участников не удаляются.
- Админ может менять роли и статусы других админов. Нельзя лишать дом последнего активного админа: запрещены его выход, блокировка и понижение. Проверку и изменение выполняй в одной транзакции с блокировкой строки дома; все изменения состава и прав используют эту же блокировку.
- Админ может восстановить `left`/`blocked` в `active` без пароля дома; при восстановлении роль сбрасывается в `member`, назначение роли выполняется отдельным запросом. Смена пароля дома требует активного админа и правильного старого пароля и не меняет существующие связи участников.

- Дом — граница доступа к общим данным. Проверяй членство пользователя в доме для операций с его данными, включая получение записи по идентификатору.
- Не полагайся только на переданный клиентом идентификатор дома или фильтрацию в интерфейсе.
- Дела, заметки, счётчики, показания и коммунальные расходы должны быть связаны с соответствующим домом.
- Не придумывай роли, правила приглашений и права редактирования чужих записей без требований задачи. Если решение влияет на доступ пользователей, уточни его перед реализацией.
- Храни исходные показания и даты, необходимые для истории и расчёта потребления. Проверяй единицы измерения и порядок показаний; замену и сброс счётчика учитывай только по согласованным правилам.
- Для денежных значений используй точные десятичные типы, а не `float`.

## Реализация

- Логин пользователя и идентификатор дома нормализуются на бэкенде через `strip().lower()` до валидации, записи и поиска. Пробелы внутри идентификаторов запрещены. Пароли и отображаемые имена в нижний регистр не переводятся.

- Имена таблиц: сущность во множественном числе с суффиксом `_table`, например `users_table`. Таблица расширения данных родительской сущности: `<родительская сущность>_<дополнительная сущность>_table`, например `users_info_table`.
- Учётные данные пользователя и профиль хранятся отдельно: `users_table` и `users_info_table`, связь один к одному через `users_info_table.user_id` (PK и FK). При регистрации профиль создаётся атомарно с пользователем, `name = null`; `username` уникален.
- Пароли хэшируются через `pwdlib`, JWT выпускаются и проверяются через `PyJWT`; срок действия access-токена — 15 минут. Изменение пароля требует проверки старого пароля, изменение профиля доступно только самому пользователю. Просмотр другого пользователя требует токена и возвращает логин, вложенный профиль `additional_info` с именем, `created_at` и `updated_at`. Профиль загружай через ORM-связь `User.info` с явной предварительной загрузкой; ORM-модели преобразуй в DTO внутри репозитория. Даты доступны также в собственном профиле: `created_at` — создание учётной записи, `updated_at` — последнее изменение учётной записи или профиля.

- Предпочитай простую модульную структуру. Наличие нескольких функциональных областей само по себе не требует микросервисов.
- Следуй принципам чистого кода: осмысленные имена, небольшие функции, одна ответственность у модуля, явные зависимости и отсутствие дублирования.
- Размещай части API в отдельных осмысленных директориях: `src/routes/`, `src/services/`, `src/repositories/`, `src/dto/`, `src/schemas/`. Внутри группируй модули по предметной области.
- `routes` отвечает за HTTP, зависимости FastAPI, статусы и преобразование результатов в ответы. `services` — за бизнес-логику и сценарии использования. `repositories` — за запросы к хранилищам.
- `dto` содержит внутренние структуры передачи данных между слоями без зависимости от FastAPI и ORM. `schemas` содержит Pydantic-схемы запросов и ответов API. Не передавай HTTP-схемы и ORM-объекты как внутренний контракт сервисов.
- Направление вызовов: роут → сервис → репозиторий. Сервисы и репозитории не должны импортировать роуты или выбрасывать `HTTPException`; SQL и операции с БД не должны находиться в роутах.
- `src/main.py` оставляй точкой сборки приложения: создание FastAPI, lifecycle и подключение роутеров. Конфигурацию и инфраструктуру БД храни отдельно от HTTP-слоя.
- Не создавай абстракции и классы без практической необходимости. Не добавляй проходные слои для каждой операции автоматически; соблюдай границы ответственности.
- Валидируй входные данные и возвращай понятные ошибки API.
- Изменения схемы базы данных оформляй миграциями после появления инструмента миграций в проекте.
- Конфигурацию окружения передавай через переменные окружения. Не сохраняй пароли, токены и другие секреты в коде, документации и отслеживаемых файлах.
- При добавлении конфигурации предоставляй пример с безопасными значениями и описанием обязательных параметров.

## Интерфейс

- Разделяй React-код на API-клиенты, авторизацию, общие компоненты и функциональные области. Не объединяй приложение в один компонент.
- Все формы и сообщения интерфейса — на русском. Логин дома в интерфейсе называется «Идентификатор дома».
- При регистрации, создании дома и смене пароля пользователя/дома обязательно подтверждение пароля на фронтенде и бэкенде. Для создания — `password_confirmation`, для смены — `new_password_confirmation`; несовпадение возвращает 422.
- Токен хранится в `sessionStorage`; при его отсутствии, истечении срока или ответе API 401 открывай `/auth`. Права проверяются бэкендом, скрытие кнопок не заменяет проверку.
- В списке участников показывай имя, если оно заполнено, иначе username. В карточке доступны и имя, и логин. Админские действия показывай только активному админу.
- Дома с участием `left` и `blocked` остаются в списке. Их страницы показывают данные дома и своё участие, но не список участников. Для `left` доступно повторное вступление по паролю.
- Поддерживай телефон и ПК, клавиатурную навигацию, подписи полей, фокус в модалках, состояния загрузки и понятные ошибки. Не добавляй пока разделы дел и коммунальных услуг.
- Проверяй frontend командами `npm run build` и `npm run format:check` из `frontend/`; npm-зависимости фиксируй в `package-lock.json`.
